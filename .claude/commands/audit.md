# /audit — adversarial review

You are auditing this repository **against the client's interests**, not the
previous session's. Assume the previous session was competent, in a hurry, and
motivated to report success. Your job is to find what it got wrong or quietly
skipped.

**Report what is actually broken. An honest "this is failing and here is why" is
worth more than a confident summary.** If you find nothing in a section, say so
in one line and move on — do not manufacture findings to look thorough.

Read `CLAUDE.md` first. Then work the passes below. Verify by running commands
and reading code, never by trusting a comment, a docstring, or this file.

---

## Pass 1 — Do the claims hold?

Run these and paste real output. Do not summarise.

```bash
pnpm typecheck && pnpm lint && pnpm test && pnpm build
```

Then, with a built app running on :3000 and `VERIFY_ADMIN_EMAIL` /
`VERIFY_ADMIN_PASSWORD` set: `pnpm verify:e2e`.

Then open `docs/PHASE_PLAN.md`. For every slice marked **DONE**, take each
acceptance criterion and prove it independently. A checked box is a claim, not
evidence. Specifically hunt for:

- Criteria checked off that the tests do not actually cover
- Tests that assert a mock rather than real behaviour
- Tests that pass because they skip (does anything `skip` or `runIf` silently?)
- Anything marked done that only works on the happy path

---

## Pass 2 — The four hard constraints

These override everything. A violation here is a stop-work finding.

**Fabrication.** Grep the rendered site and the source for invented proof:
reviews, testimonials, customers, logos, events, awards, press, staff, vendors,
statistics, counts, "trusted by", "as seen in". Check for placeholder people and
stock photography of humans. Check that every number displayed traces to real
data.

**Transportation honesty.** This is the highest-liability item — CGS §13b-101
turns on whether the business *represents itself* as transporting passengers for
hire, at up to $1,000/day/violation.

```bash
grep -rniE "our (fleet|vehicles|buses|limos|drivers|chauffeurs)|we (provide|operate|offer) (transport|shuttle)|book our (bus|limo|shuttle)" src/ docs/
```

Also check: is "Fleet" used as a nav label or heading anywhere? Is there vehicle
imagery without a "representative" caption? Is the footer disclosure still
present and unsoftened? Is there any standalone transportation page?

**Evidence classes.** Every research conclusion in `/docs` must be labelled
VERIFIED FACT / RESEARCH OBSERVATION / STRATEGIC INFERENCE / RECOMMENDATION.
Find inference presented as fact. Pay particular attention to anything sourced
while `developers.google.com`, `nextjs.org` and the CT/FMCSA domains were
egress-blocked — those are flagged in `docs/DECISIONS.md` and must stay flagged.

**Doorway pages.** Is any page generated by substituting a town or venue name
into a template? Does every location or venue page carry substantial
location-specific usefulness? Would you defend it to a Google reviewer?

## Pass 3 — Security

Do not trust `docs/SECURITY.md`. Verify each claim in code.

- Does **every** admin page and **every** admin action call `requireAdmin()` /
  `requireAdminOrNull()` itself? A layout guard is not a boundary.
  ```bash
  grep -rn "use server" src/app --include=*.ts | cut -d: -f1 | sort -u
  ```
  For each, confirm the auth check inside the function body.
- Can any server action be called with a hand-crafted payload to reach data it
  should not? Are submitted enum values re-validated server-side?
- Is any secret reachable from a client bundle? Is `server-only` present on
  every module that reads one?
- Are raw client IPs stored anywhere? Are cookies `HttpOnly` and `Secure`?
- Is rate limiting actually applied on every public write path?
- Does an error message anywhere reveal whether an account exists?
- **Check the known-gaps list at the bottom of `docs/SECURITY.md` is still
  accurate and has not silently grown.** CSP in particular is still absent.

---

## Pass 4 — The money path specifically

This is the revenue path. Break it deliberately.

- Stop PostgreSQL, submit the form. Does the customer see an honest failure with
  a contact route and an incident id — or a silent success?
- Submit with JavaScript disabled. Does it work?
- Submit garbage: oversized fields, wrong enums, a past date, min > max guests,
  a missing form token, a replayed token, an instant submission.
- Does a rejected submission preserve what the customer typed?
- Is `response_due_at` set on every inquiry, and does the overdue flag fire?
- Does the SLA number published on the site match the one the system enforces?
  They must read from one source.
- If email is unconfigured, does anything anywhere imply an email was sent?

---

## Pass 5 — Frontend and accessibility

- Every public page at **375px**: any horizontal overflow?
- Complete every critical flow with the **keyboard only**. Is focus always
  visible? Any trap? Does the skip link work?
- Exactly one `h1` per page; no skipped heading levels.
- Every form control has a real `<label for>`, not a placeholder as a label.
- Errors wired with `aria-describedby` and `aria-invalid`, in a live region.
- Contrast in **both** light and dark themes.
- Does anything look like a template? Default fonts, generic card grid,
  purple-on-white gradient, glassmorphism — all disqualifying.
- Any component inventing a value instead of consuming a design token?
- Console errors or failed requests on any page?

---

## Pass 6 — SEO and structured data

- Correct canonical on every public page; no accidental `noindex`.
- Admin genuinely non-indexable (meta directive *and* header).
- Sitemap lists only routes that exist and are indexable. No orphans.
- Structured data matches `docs/DECISIONS.md` D-012: `Organization` without an
  address, `BreadcrumbList` where breadcrumbs are visible. **No**
  `AggregateRating`, `Review`, `FAQPage`, `Event` on a service page, or
  `LocalBusiness` without a real published address.
- Does any schema describe content not visible on the page?
- Is metadata prerendered into `<head>` rather than streamed into `<body>`?

---

## Pass 7 — What the docs are hiding

- Is `CLAUDE.md` still under 200 lines and still pointers rather than content?
- Does `docs/PHASE_PLAN.md` reflect reality, including blockers?
- Are the blockers from the last session report still open, or silently dropped?
- Read `docs/DECISIONS.md` for decisions whose **revisit condition has now been
  met** — particularly D-010 (TypeScript 5.9 / ESLint 9 pins), D-011
  (`cacheComponents`), and D-012 (structured data, pending re-verification
  against `developers.google.com`).
- Is there a decision that was made in code but never recorded here?

## Output

Report findings grouped by severity, most severe first:

**BLOCKING** — violates a hard constraint, loses leads, or exposes data.
**SERIOUS** — real defect, wrong behaviour under a plausible condition.
**MINOR** — quality, consistency, polish.
**STALE** — documentation that no longer matches the code.

For each: what is wrong, the file and line, how you verified it, and the
smallest fix. Then state plainly whether the repository currently meets the
definition of done in `CLAUDE.md`.

Do not fix anything during the audit unless asked. Find and report first.
